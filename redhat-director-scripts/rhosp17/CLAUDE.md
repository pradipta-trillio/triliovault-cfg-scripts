# RHOSP 17 Deployment Scripts

## Overview
Deployment scripts for TrilioVault (T4O) on Red Hat OpenStack Platform 17.1 (Wallaby release).
RHOSP 17 uses TripleO for deployment — services are configured via Puppet manifests and orchestrated via Heat templates.

Reference: https://docs.redhat.com/en/documentation/red_hat_openstack_platform/17.1/html/installing_and_managing_red_hat_openstack_platform_with_director/index

RHOSP 17.1 was not supported in T4O 6.2.x. The 6.3 support (TVAULT-7926) was built on `dev-stable/6.3`, whose rhosp17 tree already matched `maint/6.1` (6.1.8) plus the 6.3 template changes.

## How a service reaches a container
- `config_settings` in a service yaml become node hiera on every node of a role carrying that service. TripleO merges all services' settings on a role into one hiera file, so **the four WLM yamls must set identical `trilio::wlmapi::*` values**.
- `puppet_config.step_config` runs inside `config_image` (container-puppet). Output lands in `/var/lib/config-data/puppet-generated/<config_volume>`, is bind-mounted read-only, and kolla `COPY_ALWAYS` copies `<config_volume>/*` → `/`. A file resource added to `trilio::wlmapi::config` therefore reaches all four WLM containers, including the pacemaker cron bundle, with no service-yaml change.
- Any image used as `config_image` must contain puppet, which `openstack-base:17.1` does. The RHOSO 18 base does not, which is why DMS has its own `Dockerfile_rhosp17.1`.

## T4O 6.2+ model on RHOSP 17.1 (DMS)
- **Backup targets are not Heat parameters any more.** They are workloadmgr DB records created after deploy (`workloadmgr backup-target-create`, or Horizon) and mounted on demand by DMS. `TrilioBackupTargets`, the object-store service, the per-target `[<bt>]` sections/`enabled_backends` in wlm.conf and the NFS mount loops in the start scripts were all removed. `enabled_backends = ""` is rendered, matching RHOSO18. An old env file that still carries `TrilioBackupTargets` or the 5.2 `TrilioBackupTargetType`/`NfsShares`/`S3*` is harmless: Heat ignores unknown `parameter_defaults`.
- **`OS::TripleO::Services::TrilioDms` must be in roles_data on every role that runs TrilioWlm* (Controller) or TrilioDatamover (Compute).** It is one service for both roles, because Kolla's ctlplane and dataplane server confs are identical. `TrilioObjectStore` is mapped to `OS::Heat::None` so a roles_data that still lists it keeps validating during an upgrade.
- **`node_id` = `hiera('nova::host', hiera('fqdn_canonical'))`, on both the DMS server and the WLM/DMAPI client.** DMAPI addresses compute mount requests to `dms.<OS-EXT-SRV-ATTR:host>`. On RHOSP 17.1, `nova::host` = `fqdn_canonical` = the FQDN nova reports (verified on uc17qa1). WLM sends its own requests to its own `node_id`, so the controller's server and client must use the same lookup.
- **RabbitMQ:** DMS uses the overcloud RPC broker (`oslo_messaging_rpc_*` hiera, user `guest`, vhost `/`). `dms_rabbitmq_url()` builds `rabbit://u:p@h1:port,u:p@h2:port//[?ssl=1]`; DMS splits the comma form and fails over. Server and client must render the identical URL, so always use the function. RHOSP 17.1 runs RabbitMQ 3.9 with classic mirrored queues (`ha-all`), so the queue settings default to `classic`/non-durable. The `trilio_dms` exchange is always durable, and DMS recreates a queue whose arguments don't match.
- **The DMS client's `db_url` is the workloadmgr DB, on DMAPI too (TVAULT-7361).** That is why `triliovault-datamover-api.yaml` carries the `WlmApiDb*` parameters.
- **The DMS container needs `ipc: host`, `/var/lib/nova:/var/lib/nova:shared` and the host `/run`.** The mount root stays `/var/lib/nova/triliovault-mounts`, which nova, the datamover and WLM already share and which keeps 5.2/6.x snapshot paths valid. `/run/dms` comes from `/etc/tmpfiles.d/trilio-dms.conf` (5 dirs, `certs` at 0700, age `-`) written in `host_prep_tasks` — see `kolla-ansible/CLAUDE.md` "DMS runtime directory" for why it is never baked into the image.
- **No cloud-trust container.** From 6.2, `trust-create` needs a backup target first, so `triliovault_wlm_api_cloud_trust_init` would fail a fresh deploy at step 5 (RHOSO18 dropped its job for the same reason, commit 1e4e2305). After creating a target, run `podman exec triliovault_wlm_api /opt/triliovault/create_wlm_cloud_trust.sh`.
- **S3 needs Barbican in the overcloud.** DMS fetches the `secret_ref` URL itself from every node, so the href must use an interface every controller and compute can reach. `update_backup_targets.sh` defaults to `BARBICAN_INTERFACE=public` (DevOps Reference §9.1); use `internal` when computes cannot reach the public VIP, which is typical with network isolation.
- **NFS mount path continuity:** WLM 6.x names the mount `base64(urlparse('//'+export).path)`, the same value the 5.2/6.x start scripts used (e.g. `/home/rhosp` → `L2hvbWUvcmhvc3A=`). Re-creating a 5.2 NFS target with the exact old export string keeps existing snapshots resolvable.

## Upgrade 5.2.x / 6.1.x → 6.3
1. `scripts/collect_backup_targets.sh -e <old trilio_env.yaml> [-n <old trilio_nfs_map.yaml>] [-c <old puppet/trilio/files>]`. It reads both formats and writes `existing_backup_targets.yaml` (mode 0600, holds S3 keys):
   - 5.2: the single target, `action: create`.
   - 6.x S3: `action: add_secret_ref`.
   - 6.x NFS: `action: none`.
   - Multi-IP NFS targets are flagged for manual handling.
2. `workloadmgr disable-global-job-scheduler`, then run the stop scripts on the controllers and computes.
3. `ansible-playbook -i ~/overcloud-deploy/<stack>/tripleo-ansible-inventory.yaml scripts/cleanup_backup_targets.yml`. It removes object-store units, containers and config, and lazy-unmounts FUSE/NFS under the mount root. It refuses to run once `triliovault_dms` is up.
4. Prepare the images (now including `trilio-dms`), upload the puppet module, add `TrilioDms` to roles_data and remove `TrilioObjectStore`, then run `overcloud deploy` with the new `trilio_env.yaml`.
5. On one controller, as root: `update_backup_targets.sh -f existing_backup_targets.yaml`. It creates 5.2 targets and attaches Barbican secrets to 6.1 S3 targets. It is idempotent, and `DRY_RUN=1` previews.
6. Run `enable-global-job-scheduler` and verify.

## Known pre-existing quirks (left as-is)
- Several service yamls have duplicate parameter keys (`CephClientUserName`, `EnableInternalTLS`, `DefaultPasswords`) and trailing tabs. Heat parses them with libyaml, so validate with `yaml.CSafeLoader`, not the pure-Python `SafeLoader`, which rejects the tabs.
- The lab undercloud uc17qa1 (172.30.0.2) is shared with QA. As of 2026-11-04 it ran T4O 5.2.7 plus a hand-started prototype `triliovault_dms_server` on all nodes. Remove that prototype before deploying the tripleo DMS service, because both would consume the same `dms.<node>` queues.

## Deployment Flow
1. `scripts/prepare_trilio_images.sh <undercloud> <tag>` — pull/push images, rewrite image lines in `trilio_env.yaml`
2. `scripts/generate_passwords.sh` — create `trilio_passwords.yaml`
3. `scripts/upload_puppet_module.sh` — upload `puppet/trilio`
4. Add the Trilio services to roles_data (Controller: TrilioWlm*, TrilioDatamoverApi, TrilioDms; Compute: TrilioDatamover, TrilioDms)
5. `openstack overcloud deploy ... -e trilio_env.yaml -e trilio_defaults.yaml -e trilio_passwords.yaml -e <endpoint env>`
6. Create a backup target, then the cloud admin trust
